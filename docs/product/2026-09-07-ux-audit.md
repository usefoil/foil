# Foil UX audit — September 7, 2026

Foil has useful dictation and recovery capabilities, but the interface asks users to understand too much of the implementation before experiencing the payoff. The largest opportunities are trustworthy state, a guided first dictation, and local model setup. Visual polish comes after those.

## Scope and confidence

- Reviewed repository HEAD `78ff194`: onboarding, app shell, Home, menu, recording preferences, providers, cleanup, history, status feedback, paste routing, and relevant tests.
- Inspected installed `/Applications/Foil.app`, displaying version 1.13.13 (48), through screenshots and accessibility state: General, Recording, Cleanup, Home, and the idle audio capsule. This is an existing configured installation, not a fresh-user session; it is not assumed to be built from HEAD.
- Onboarding findings come from source and existing test inspection. No fresh macOS permission cycle, real audio upload, model benchmark, or cross-app paste test was performed for this audit.
- Compiled an isolated executable against the actual history model to test retention across reconstruction. Only temporary synthetic data was used.
- No implementation or user preferences changed. Screen contents containing personal history were not copied into this report.

## 1. Fix retention preferences before polishing privacy copy

**Confirmed implementation defect, highest priority.** Choosing History retention → Off changes only the in-memory history object. Startup creates a new object with `isPersistenceEnabled: true` and `retentionLimit: 500`. Choosing 100 likewise does not persist the preference.

Evidence: `Foil/SettingsView.swift:1904`, `Foil/TranscriptionHistory.swift:59`, and `Foil/FoilApp.swift:336`. The history JSON serializes records, not preferences. A compiled probe using the actual model and startup-equivalent reconstruction produced:

```text
After Off and reconstruction: enabled=true, records=1, fileExists=true
After choosing 100 and reconstruction: retention=500
```

The probe source and executable are at `/tmp/foil-ux-audit-20260907/HistoryPreferenceProbe.swift` and `/tmp/foil-ux-audit-20260907/history-preference-probe`. Temporary synthetic records were removed afterward.

Persist retention separately and load it before constructing the store. Prove Off and each supported limit survive process restart, including confirming that a new transcript creates no history file while Off. Also clarify that selecting Off currently clears existing history immediately; stopping future storage and deleting existing records should be explicit choices.

## 2. Define onboarding success as a working dictation

**Confirmed flow gap.** The four steps are Provider, Credentials, Accessibility, Microphone. Next does not require completion; step checkmarks mean the user advanced, not that a prerequisite passed. Get Started checks system permissions only. The existing `testOnboardingCanCompleteWhenPermissionsReadyAndApiKeyMissing` explicitly codifies finishing without a key.

Completing onboarding closes the window and starts the hotkey monitor. It does not teach the shortcut through practice or prove transcription and insertion. The separate Test Setup checks provider configuration and approximately 250 ms of microphone capture, then deletes the audio. It does not transcribe that audio or verify insertion.

Evidence: `Foil/OnboardingView.swift:239`, `Foil/OnboardingView.swift:263`, `Foil/FoilApp.swift:784`, `Foil/FoilApp.swift:1454`, `FoilUITests/FoilUITests.swift:739`.

Recommended flow:

1. **Choose how to transcribe:** On this Mac or Cloud, with plain explanations of setup, connectivity, and where audio goes. Put custom endpoints behind an advanced path.
2. **Make the selected path usable:** Download/set up a local model, or enter and validate cloud credentials inline. Allow an explicit “Finish later” without claiming readiness.
3. **Try your microphone:** Request microphone permission from an explicit action; show the input name and a live level meter.
4. **Practice the shortcut:** Show the configured key and hold/toggle behavior. Let the user record a short phrase and see its transcript in Foil.
5. **Try insertion:** Explain Accessibility immediately before enabling insertion into another app. Offer a controlled insertion test and an explicit user confirmation where verification is unavailable.
6. **Finish with the habit:** “Hold [your key], speak, release.” Show how to reopen Foil and recover the last transcript. Offer launch at login after the first success.

A same-app transcript proves only capture and transcription; keep the external insertion check distinct. Store setup progress so postponing permissions or credentials does not restart the tutorial.

This aligns with Apple's guidance to teach through experience and keep onboarding brief and optional: [Apple onboarding guidance](https://developer.apple.com/design/human-interface-guidelines/onboarding).

## 3. Make local transcription a product feature rather than a setup project

**Confirmed friction; impact on adoption is a hypothesis to test.** Local setup exposes install, build, download, and server commands. Foil already has Start/Stop and automatic server startup after installation, which is valuable. The remaining cliff is the first installation. Calling the local onboarding step “Credentials Optional” emphasizes the step the user does not need, while sending the essential setup into another window.

Evidence: `Foil/OnboardingView.swift:373`, `Foil/SettingsView.swift:1335`, `Foil/SettingsView.swift:1386`.

Near term: rename that step “Set up local transcription”; show missing prerequisites, numbered installation steps, the actual next action, and a clear connection result inside onboarding.

Larger investment: manage an approved local runtime and model download in the app, including progress, cancel/resume, disk requirements, integrity verification, failure recovery, and offline readiness. Keep external whisper servers as an advanced option. This requires packaging/distribution work; it is not merely a redesigned button.

The starter is currently Base English while speech language defaults to Auto. Ask about language before recommending a model; do not imply an English-only model supports automatic multilingual dictation. Replace “small/moderate/large download” with actual sizes from model metadata. Benchmark on supported Macs before recommending a larger default or claiming latency.

Evidence: `Foil/TranscriptionService.swift:326`, `Foil/AppState.swift:1358`.

## 4. Make “Ready” and “Delivered” mean what users think they mean

**Confirmed presentation inconsistencies; real-world failure frequency is unmeasured.**

- Home labels a fixed “API Key” row ready for keyless local providers. `isSetupReady` uses permissions plus API-key state; `refreshApiKeyState` marks keyless providers ready without a server connection check. Represent provider availability separately from credentials.
- `PasteDelivery.userMessage` correctly distinguishes command-posted paste from verified insertion. Preserve this work. However, session detail still adds “Delivered,” and the capsule maps any transient result, including clipboard fallback, to a success phase with accessibility text “Recording delivered.” Propagate the richer delivery state across every surface.
- The default paste route posts Command-V into the app active at completion. Switching apps while waiting can change the destination. This is established from routing code, not a reproduced live mispaste. The experimental original-app route should not simply become the default without compatibility proof.

Evidence: `Foil/AppState.swift:857`, `Foil/AppState.swift:1834`, `Foil/AppState.swift:989`, `Foil/AppState.swift:2115`, `Foil/PasteDelivery.swift:31`, `Foil/FloatingStatusView.swift:83`, `Foil/PasteController.swift:94`.

Recommended behavior: capture the intended destination, display it during processing, and when focus changes unexpectedly offer “Insert into [app]” or “Copy.” Prefer a clear recovery step over quietly pasting into an unrelated field. Keep experimental low-level routing off until tested across target apps.

Always offer a directly accessible last-result Copy action. With clipboard restoration on, pressing Command-V after an undetected paste failure may paste the user's previous clipboard content. Retain the last result in memory even if persistent history is disabled, with an explicit lifetime.

Acceptance scenarios: switch apps during a delayed result; close the target; reject synthetic paste; change clipboard during delivery; disable history; lose the cleanup endpoint after transcription succeeds. Confirm both actual target text and recovery behavior, not just a success icon.

## 5. Simplify Home around the next useful action

**Observed UI problems.** Recording settings showed Globe/Fn. Home simultaneously displayed “Right Command captures speech…” and “Globe/Fn” in its status card. The header is hardcoded in `Foil/FoilHomeView.swift:60`.

Home spends a prominent panel on three healthy prerequisite indicators and another on a default cleanup group. Recent transcripts appear in a narrow left column with unused space to the right in the inspected window. The source uses a two-column `LazyVGrid` with `gridCellColumns(2)` on the transcript panel; verify the intended span in the actual layout. Transcript previews have no click/copy action in Home's implementation.

Make the shortcut and an actionable state the headline. During initial setup, show one next-step card. Once ready, condense health into a status line and surface it only when something needs attention. Show microphone, transcription destination, and cleanup state in plain terms. Make recent results full-width and actionable. Put Copy before Paste Last because Copy has a predictable destination.

The actual Home has enough space; it needs a clearer hierarchy more than more panels.

## 6. Give feedback one coherent set of preferences

**Observed and source-confirmed.** General shows “Show floating status” off while a separate idle capsule remains on screen. The app unconditionally presents the live audio signifier at launch, and the other floating status can appear during recording despite its preference being off.

Evidence: `Foil/FoilApp.swift:511`, `Foil/FoilApp.swift:900`, `Foil/AppState.swift:896`.

Use one recording indicator, visible during recording and processing, with an optional idle display. Keep actionable error/recovery feedback visible independently of routine success notifications. Prefer separate clear preferences for “Show idle indicator,” “Detailed recording status,” and sounds only if each controls something users can identify.

Both setup and app shell force light appearance. Follow the system appearance by default and verify dark mode, increased contrast, reduced motion, keyboard navigation, and VoiceOver. Existing accessibility identifiers are helpful but do not establish accessible interaction quality.

## 7. Present cleanup as an outcome and vocabulary as a capability

The installed Cleanup screen leads with group management, a disabled Enabled control, app assignment, and vocabulary. The default group name truncates. This is considerable machinery before a user has chosen whether to clean up speech.

Start with “Keep my words” versus “Clean up my speech,” plus a short before/after example and the text destination. Put provider/model/prompt controls under an advanced disclosure, and app-specific behavior behind “Customize by app.” Preserve raw as the default and require an explicit choice before adding cloud cleanup to local transcription.

Vocabulary is currently stored globally but presented inside a group's detail. Its help says it applies when a cleanup profile is chosen. That is a reasonable implementation constraint, but it risks making users believe that saving a correction improves raw dictation when it does not. Show “Saved; inactive while cleanup is off” prominently. Consider a separate Vocabulary destination and, longer term, conservative local corrections or provider-supported vocabulary hints. Do not silently rewrite raw output.

Evidence: `Foil/SettingsView.swift:565`, `Foil/SettingsView.swift:705`, `Foil/SettingsView.swift:1215`, `Foil/TranscriptProcessingMode.swift:22`.

## Default recommendations

| Setting | Current default | Recommendation |
| --- | --- | --- |
| Provider | Groq | Explicit Local/Cloud choice; explain prerequisites. Do not default to an unusable local installation. |
| Local model | Base English | Language-aware recommendation, then hardware/quality guidance backed by benchmarks. |
| Shortcut | Right Command, hold | Keep a starting choice; practice it during onboarding and offer Toggle visibly. |
| Audio format | M4A | Keep; put format selection under Advanced. |
| Input | System default | Keep, but display the resolved device and meter. |
| Cleanup | Raw | Keep; offer an example-based opt-in after first dictation. |
| Clipboard | Restore previous contents | Keep with a reliable, easy last-result Copy action. |
| History | 500 records | Fix persistence first; consider a disclosed 100-record default with a clear Off option. |
| Usage metrics | On, local | Prefer opt-in when opening Insights; explain app-name retention separately from history. |
| Idle indicator | Always presented | Default hidden; show active recording/processing and actionable failures. |
| Experimental routing/queue/bridge | Off | Keep off. |
| Other browser audio control | Off | Keep off; this does not control all system media. |

Rename Storage to “Privacy & History” or “Privacy & Data.” Move Insights below History and reduce the eight preference destinations; the current Paste page contains only one toggle while related routing choices live in Experimental. Consolidate without bringing experimental options into the primary flow.

## Suggested delivery sequence and proof

1. **Trust fixes:** persistent retention, truthful delivery/capsule states, dynamic hotkey copy, actionable provider health. Verify restart and failed-delivery cases.
2. **Activation:** guided first dictation, inline credentials/local setup, microphone meter, practice shortcut, clear completion. Run fresh-user tests for local and cloud paths, including denied permissions and unavailable providers.
3. **Everyday experience:** last-result recovery, simpler Home, coherent indicator preferences, basic cleanup with advanced disclosure, vocabulary activation clarity.
4. **Local adoption:** managed runtime/model download, language/hardware recommendations, interrupted-download and offline-relaunch verification.
5. **Visual/accessibility polish:** system appearance, contrast, typography hierarchy, keyboard/VoiceOver review, actual window-size layout checks.

Validate the product hypotheses with a small observed usability round: include local-first users unfamiliar with Terminal and users with an existing cloud key. Watch without coaching. Measure time to first transcript and first external insertion, where help was needed, whether they remember the shortcut the next day, and whether they can recover from a failed paste. Do not infer ease of use from setup badges or deterministic fixture tests.

## Evidence receipt

**Claim:** the recommendations address current implementation and observed UI rather than only design documents.

**Strongest failure modes checked:** history settings might already persist elsewhere; setup testing might already perform real transcription/insertion; live status feedback might already respect the visible preference; Home's instructions might track the user's selected shortcut.

**Evidence:** repository-wide symbol searches and caller inspection; compiled real-model history probe with synthetic temporary storage; direct inspection of setup-check implementation and existing onboarding tests; screenshots/accessibility state from installed General, Recording, Cleanup, and Home; inspection of both status-panel paths.

**Residual risk:** no full fresh-user onboarding, cloud transcription, local model installation, hardware latency benchmark, or live cross-app failure reproduction. Proposed conversion and usability benefits require observed user testing. Installed-build observations and HEAD findings are distinguished above. This audit is not a release certification.
